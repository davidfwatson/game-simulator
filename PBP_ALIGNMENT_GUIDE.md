# PBP Alignment Guide

This guide covers explicit commentary draws and source-backed wording alignment.
The play index map, half-inning checklist, and progress table below retain the
earlier example-3 alignment history. Those indices apply only to
`test_fixture_pbp_example_3.json` and `pbp_example_3.txt`.

For the 17 newly reconstructed broadcasts, edit the reviewed ledgers in
`transcript_games/` and follow [their workflow](transcript_games/README.md).
The generated fixtures live in `examples/transcript_games/`; they are separate
from the four original PBP references and the 78 representative helper cases.

Wording choices live in `commentaryRng` lists; timestamps only represent timing.
The new full-broadcast catalog covers 1,106 observed appearance records, 3,727

`python pbp_match_report.py --check` checks all three catalogs when no example

Register new sources and reviewed coverage/wording minimums in

## Key Principles

**For the historical example-3 fixture, fix JSON data errors when you find them.** It was bulk-generated by
`stitch_fixture.py` from draft innings and may have errors — wrong `result.event`,
wrong `eventType`, missing runner entries, wrong fielder credits, etc. If you
notice the JSON doesn't match the target game, just fix it. The source of truth
for that fixture is `pbp_example_3.txt` and `draft_innings/inning_N.json`.
For the full transcript corpus, preserve the cleaned source files and correct
`transcript_games/episode_NNN.json`, then recompile/refit. Retain conflicting
recaps, uncertain counts, and omitted intervals in `notes`/`gaps`; do not invent
pitches or measurements to make a rendering match.

**Ignore structural line-break and TTS differences.** The target text has
`[TTS SPLIT HERE DELAY:Ns]` markers and sometimes combines multiple pitches on
one line. The renderer generally separates pitches and emits its own TTS markers.
The comparison tools normalize structural differences and report content-only
line matching separately. Focus on selecting the right words through draws and
factually appropriate templates; inspect timing/layout independently.

**The target text has been cleaned but may still have minor errors.** The
transcript was cleaned of major speech-to-text errors, but some ambiguous
phrases may remain. If a phrase in the target looks garbled, use the closest
clean baseball phrasing that matches the intended meaning. Don't add
unnatural phrasing to `commentary.py` templates.

**For the historical example-3 checklist, work one half-inning at a time.**
Coordinate edits before committing and update its progress table below. Full
transcript follow-ups use source ranges and the separate ledger workflow.

## The Tools

All tools live in `pbp_tools.py`. Key commands:

| Command | What it does |
|---------|-------------|
| `inspect-play FILE --play N [-v]` | Shows all seed points and RNG choices for play N. Use `-v` to see the full list of options at each choice point. |
| `set-choice FILE --play N --point POINT --set STREAM:CALL:INDEX` | Updates the commentary draw list at a point so a specific template is selected. Preserves other selections at the same seed point. |
| `search "phrase"` | Searches all template pools for a substring match. |
| `list-pool POOL_PATH` | Lists all templates in a pool (e.g., `narrative_templates.Single.default`). |
| `diff FILE TARGET_FILE` | Shows line-by-line mismatches and similarity stats. |

## How Commentary Draws Work

The renderer uses the persisted `gameData.commentarySeed` (default zero) or an
explicit renderer/CLI seed. Each point and stream gets a deterministic seed
based on its identity, independent of timestamps. The four streams are `play`,
`pitch`, `flow`, and `color`.

A fixture may store an unlimited list of nonnegative integer draws per stream:

```json
"commentaryRng": {
  "play_outcome": {
    "play": [3, 12, 1],
    "pitch": [],
    "flow": [25],
    "color": []
  }
}
```

Each call consumes one whole integer. `choice(pool)` selects
`pool[draw % len(pool)]`; `random()` returns `(draw % 100) / 100`.
Calls do not share digits. Missing or exhausted lists use normal seeded
randomness, so long sequences retain variation. Input lists are never mutated.

| Point | Metadata owner | Controls |
|-------|----------------|----------|
| `init` | `gameData.commentaryRng.init` | Pregame, lineups, welcome |
| `play_start` | `play.commentaryRng.play_start` | Batter intro, matchup, transitions |
| `event_N` | `play.playEvents[N].commentaryRng.event` | Connector, pitch, count |
| `play_outcome` | `play.commentaryRng.play_outcome` | Hit/out description, runner status |

`inspect-play` shows the observed calls; `set-choice` can edit any observed
call, including calls after the second and pools larger than 100 entries.
Use `--point init` for pregame choices. `set-gate` controls probability draws.
These commands materialize observed choices before editing, preserving the
other selections at the point. Editing a gate can change which later calls
occur, so inspect the resulting text and realign those calls when needed.

Use stable list indices by appending new templates. Stored selected indices
continue choosing the same existing template when a pool grows. Reordering or
removing templates, or inserting RNG calls into a stream, requires reviewing
and rebuilding affected fixture selections. Generated output can change as
pools grow; refresh its snapshots after reviewing the changes.

## Pre-Game Text

Pregame uses the `color` stream at `init`. All calls are controllable, including
each lineup slot; there is no two-call limit. Station and welcome introductions,
lineups, manager text and pregame color come from these draws. Weather still
comes directly from `gameData.weather`; team and venue facts come from game data.

## Hit Category System (How Outcome Templates Are Selected)

This is the single most important thing to understand for aligning hit outcomes.

Outcome selection considers source facts and explicit category annotations as
well as simulated metrics. For a full broadcast ledger, record a supported
`hit.categoryOverride` (for example, `bloop`) together with the known trajectory
and field location. The compiler copies `hit` into the in-play event's
`hitData`. Do not manufacture `launchSpeed` or `launchAngle` just to reach a pool.
Special situations also require their actual runner movements, fielder credits,
or outcome flags; a desired phrase is not evidence that the situation happened.

For simulated games or older synthetic helper cases with numeric data,
`_get_batted_ball_category()` in `renderers/base.py` uses `launchSpeed` and
`launchAngle` on the in-play event. The table below documents those metric-based
categories. An absent measurement remains unknown in a transcript fixture.

### Category thresholds:

| Outcome | Category | Condition |
|---------|----------|-----------|
| Single | `bloop` | ev < 90 AND 10 < la < 30 |
| Single | `liner` | ev > 100 AND 0 <= la < 10 |
| Single | `grounder` | ev > 95 AND la < 0 |
| Single | `default` | anything else (or ev/la missing) |
| Double | `liner` | ev > 100 AND la < 15 |
| Double | `wall` | ev > 100 AND la >= 15 |
| Home Run | `screamer` | ev > 105 AND la < 22 |
| Home Run | `moonshot` | ev > 100 AND la > 35 |
| Groundout | `soft` | ev < 85 |
| Groundout | `hard` | ev > 100 |
| Flyout | `popup` | (ev < 95 AND la > 50) OR (ev < 90 AND la > 40) |
| Flyout | `deep` | ev > 100 AND la > 30 |

### Selecting a source-supported category

For a transcript that explicitly describes a bloop single to left, use:

```json
"hit": {
    "trajectory": "fly_ball",
    "location": "LF",
    "categoryOverride": "bloop"
}
```

This is ledger syntax. In a compiled Gameday fixture the same object is
`playEvents[N].hitData`. Only record the location if it is known. For manually
authored original fixtures, edit the in-play event directly or use the category
tool; numeric scenario inputs in older examples do not become broadcast facts.

### RNG calls before the template choice

Branch gates, descriptor choices, and outcome choices can consume different
calls depending on the situation. Inspect the actual path with
`inspect-play --play N -v`; use its stream and call number instead of assuming
that an outcome template is always the first draw.

## How the Renderer Builds a Play's Output

Understanding this sequence prevents most alignment mistakes. The renderer
outputs text for each play in this exact order:

```
┌─────────────────────────────────────────────────────────────┐
│ 1. INNING HEADER (if first play of half-inning)            │
│    "Top of the third inning here at Goodhue Field..."      │
│    Seed: play_start → rng_color                            │
├─────────────────────────────────────────────────────────────┤
│ 2. BATTER INTRO (from play_start seed)                     │
│    "And Joe Bill Silver steps in with runners on first      │
│     and second, nobody out."                                │
│    Pool: batter_intro_leadoff (0 outs, 0 runners)          │
│          batter_intro_empty (>0 outs, 0 runners)           │
│          batter_intro_runners (any runners on base)        │
│    Seed: play_start → rng_flow                             │
│    Variables: {batter_name}, {team_name}, {outs_str},      │
│              {position}, {pitcher_name},                   │
│              {runners_str} (for runners pool only)         │
├─────────────────────────────────────────────────────────────┤
│ 3. MATCHUP LINE (conditional, ~20% of the time)            │
│    "Righty against the lefty."                              │
│    Seed: play_start → rng_color (random() < 0.2)           │
│    Format: "[batter hand] against [pitcher hand]"          │
├─────────────────────────────────────────────────────────────┤
│ 4. PITCH EVENTS (one per playEvents entry)                 │
│    Each pitch event generates:                             │
│    a) Connector: "And the pitch..." / "And the oh-one..."  │
│       Pool: pitch_connectors_00 (0 balls, 0 strikes)       │
│             pitch_connectors (count > 0-0)                 │
│             pitch_connectors_stretch (runners on base)     │
│       Seed: event_N → rng_flow                             │
│    b) Pitch description: "Fastball, called a strike"       │
│       Pool: pitch_locations.strike.* (called strikes)      │
│             pitch_locations.ball.* (balls)                 │
│             pitch_locations.foul (fouls)                   │
│       Seed: event_N → rng_pitch                            │
│    c) Count: "oh and one" / "one and two"                  │
│       (Generated by get_spoken_count(), not a template)    │
├─────────────────────────────────────────────────────────────┤
│ 5. OUTCOME (from play_outcome seed)                        │
│    "Ground ball to third, this could be two!"              │
│    Pool: narrative_templates.{Outcome}.{category}          │
│          e.g., Single.bloop, Groundout.default,            │
│          Double Play.default, Flyout.popup                 │
│    Seed: play_outcome → rng_play                           │
│    Variables: {batter_name}, {direction}, {direction_noun}, │
│              {pitch_type}, {fielder_name}, {result_outs},  │
│              {out_context_str}                              │
├─────────────────────────────────────────────────────────────┤
│ 6. RUNNER STATUS (only for Singles, Doubles, Triples)      │
│    "Yamaguchi starts things off with a leadoff single."    │
│    Pool: leadoff_single, single_one_out, etc.              │
│    Seed: play_outcome → rng_play                           │
│    NOT appended for outs (Groundout, Flyout, Double Play)  │
└─────────────────────────────────────────────────────────────┘
```

### Key implications for alignment:

- **Transition text like "So first and second, nobody out for Silver" is part
  of Play 9's batter intro (step 2), NOT part of Play 8's outcome (step 5).**
  When the target text flows "...base hit. So first and second, nobody out for
  Silver", the text after the hit description belongs to the next play.

- **Runner status depends on the outcome and recorded movements.** Hits and
  walks have status routes; a batter staying safe after a forceout or double
  play must be supported by the runner data. Do not add safe-arrival wording
  solely because a target phrase sounds appropriate.

- **The matchup line (step 3) is generated by the renderer, not a template pool.**
  "Righty against righty" is hardcoded logic based on `batSide` and `pitchHand`
  in the play's `matchup` block. To change it, fix the matchup data, not a template.

- **The `batter_intro_runners` pool has special handling** for `{runners_str}`.
  The variable renders differently depending on runner count:
  - 1 runner: `"a runner on first"` or just `"first"` depending on template
  - 2 runners: `"runners on first and second"` or `"first and second"`
  - 3 runners: `"the bases loaded"`
  Check the exact rendering with `inspect-play -v` before writing templates.

### Template variables reference:

| Context | Available variables |
|---------|-------------------|
| Batter intro (no runners) | `{batter_name}`, `{team_name}`, `{outs_str}`, `{position}`, `{pitcher_name}` |
| Batter intro (runners) | `{batter_name}`, `{runners_str}`, `{outs_str}`, `{pitcher_name}` |
| Pitch connectors | `{count_str}`, `{count_str_cap}`, `{pitcher_name_last}` |
| Outcome templates | `{batter_name}`, `{direction}`, `{direction_noun}`, `{pitch_type}`, `{pitch_type_lower}`, `{pitch_velo}`, `{fielder_name}`, `{result_outs}`, `{result_outs_word}`, `{out_context_str}` |
| Runner status | `{batter_name}`, `{inning_context}` |

## Gotchas

**Verbal locations belong in `details.location`; numeric zones belong in `details.zone`.**
The full-game compiler copies a ledger pitch's semantic `location` into the
former. Use `inside`, `outside`, `high`, `low`, `dirt`, or a supported combined
location for balls; called strikes also support `outside_corner`,
`inside_corner`, `corner`, `middle`, and `low`. A verbal location does not imply a
measured zone or batter handedness. Omit unknown locations.

For older numeric-zone fixtures, the renderer reads `details.zone`, not
`pitchData.zone`.
Both exist in the fixture JSON, but the renderer reads from
`playEvents[N].details.zone`. If you change the zone to switch ball pools
(e.g., `low_outside` → `high_inside`), update `details.zone`. Updating only
`pitchData.zone` has no effect.

**Fielder credits go on `play.runners[].credits`, not on the play itself.**
The full-game compiler builds these credits from reviewed fielder sequences.
Preserve the players, positions, assist/putout roles, and order of outs rather
than adding a fielder name solely to select a preferred phrase.

**Append templates and review their context.** Stored choice indices preserve
existing selections when a pool grows. Reordering entries changes their meaning;
a new branch or call can also shift later draws. Review rendered fixture changes
and generated snapshots after any wording change.

**Switch hitters: check the target text for bat side.** The target text often
says "he'll bat left against [pitcher]" — use this to set the correct `batSide`
in the matchup. For switch hitters vs RHP, batSide is typically `L`.

**Check multi-word names in the actual rendering.** Different helpers format
names differently. Inspect names such as "Del Greco" and "De Jesus" in the
selected path instead of assuming that a global `lastName` field controls it.

**Use simple single-line pbp tool calls.** Don't write multiline bash commands.
Each `set-choice`, `inspect-play`, or `search` should be its own simple call.

**Work on a branch and create a PR.** Don't commit directly to main.

**Review measured baselines after alignment.** The catalogs in
`pbp_comparison.py` record the relevant coverage and wording minimums. Measure
with the report tools, review the changes, and ratchet only the appropriate
catalog's minimums. Keep factual coverage checks exact.

**`hitData` goes on the last pitch event, not the play level.** The renderer
reads `launchSpeed`/`launchAngle` from `playEvents[last].hitData`, not from
any play-level hitData. If `inspect-play` still shows the wrong category pool
(e.g., `Single.default` instead of `Single.grounder`), you're putting the
hitData in the wrong place.

**Don't change player data globally for one play.** If a matchup looks wrong,
it's almost certainly a `batSide` or `pitchHand` error in that specific play's
`matchup` block — not a global player data issue. Fix it in the play's matchup,
not in `gameData.players`.

## Task Loop (Per Half-Inning)

### 1. Identify the target text

Find the half-inning boundaries in `pbp_example_3.txt`. The text flows
continuously — look for inning-transition phrases like "Bottom of the third"
or score summaries.

### 2. For each play in the half-inning

#### a) Inspect the current rendering

```bash
python pbp_tools.py inspect-play test_fixture_pbp_example_3.json --play N -v
```

This shows:
- Every seed point (with timestamp and JSON path)
- Every RNG choice made (which pool, which index, which template was selected)
- The full list of available templates at each choice point (with `-v`)
- The current rendered text for this play

#### b) Compare to target text

Read the corresponding section of `pbp_example_3.txt` and compare line by line.
Identify each mismatch:

- **Wrong template selected**: The target phrase exists in the pool but a different
  index was chosen → use `set-choice`.
- **Missing template**: The target phrase doesn't exist in any pool → add it to
  `commentary.py`, then use `set-choice`.
- **Wrong hit category**: The rendered outcome says "Lined into..." but target says
  "Blooped into..." → use the supported category override and source facts
  described above; do not invent tracking measurements.
- **Structural issue**: Different line breaks, missing TTS markers, wrong
  pitcher/batter data → edit the fixture JSON directly.

#### c) Search for the target phrase

```bash
python pbp_tools.py search "drops in front of"
```

If found: note the pool name and index. If not found: the phrase needs to be
added (see step d).

#### d) Add missing templates

When a target phrase has no matching template:

1. Identify the correct pool. The pool depends on context:
   - Pitch descriptions → `pitch_locations.ball.*` or `pitch_locations.strike.*`
   - Foul descriptions → `pitch_locations.foul`
   - Batter intros → `narrative_strings.batter_intro_*`
   - Hit outcomes → `narrative_templates.{Outcome}.{category}`
   - Pitch connectors → `narrative_strings.pitch_connectors*`
   - Runner status → `narrative_strings.leadoff_single`, `single_one_out`, etc.
   - Pre-game → `radio_strings.station_intro`, `radio_strings.welcome_intro`, etc.
   - Lineup templates → `lineup_strings.batting_N`, `lineup_strings.intro_away`, etc.

2. Add the template to `commentary.py` in the appropriate list. **Add it at
   the end** of the list to minimize disruption.

3. Re-run the comparison tests. Appended templates preserve explicit existing
   indices, but new rendering branches can change call order and require
   reviewing affected fixtures with `inspect-play` and `set-choice`.

#### e) Set the draw to select the right template

```bash
python pbp_tools.py set-choice test_fixture_pbp_example_3.json \
    --play N --point play_outcome \
    --set play:1:3
```

The `--set` format is `STREAM:CALL_NUMBER:DESIRED_INDEX`:
- `STREAM`: one of `play`, `pitch`, `flow`, `color`
- `CALL_NUMBER`: which call within that stream (0-indexed, as shown by `inspect-play`)
- `DESIRED_INDEX`: the index of the desired template in its pool

You can pass multiple `--set` flags to change multiple selections at the same
seed point:

```bash
python pbp_tools.py set-choice test_fixture_pbp_example_3.json \
    --play N --point event_0 \
    --set flow:0:5 --set pitch:0:4
```

Use `--dry-run` first to preview without writing.

#### f) Fix JSON data issues

Some mismatches aren't template issues — they're wrong data in the fixture JSON:
- Wrong hit trajectory or location
- Wrong pitch type codes
- Missing source-supported hit category or required situation facts
- Missing or wrong player names in credits
- Wrong play result type

Edit `test_fixture_pbp_example_3.json` directly for these. You can also
re-run `stitch_fixture.py` after updating the relevant `draft_innings/inning_N.json`
file, but be aware this regenerates ALL plays and resets the plays’ explicit commentary draws.

#### g) Verify

Re-run `inspect-play` to confirm the rendered output now matches the target.

### 3. After completing a half-inning

Regenerate the rendered snapshot and run tests:

```bash
# Re-render the fixture to update the snapshot file
python3 -c "
import json
from renderers.narrative.renderer import NarrativeRenderer
with open('test_fixture_pbp_example_3.json') as f:
    data = json.load(f)
renderer = NarrativeRenderer(data)
with open('test_fixture_pbp_example_3.txt', 'w') as f:
    f.write(renderer.render())
"

# Run the tests
pytest test_examples_snapshot.py -k "pbp_example_3" -q
```

Also run the diff to track overall progress:

```bash
python pbp_tools.py diff test_fixture_pbp_example_3.json pbp_example_3.txt
```

## Common Patterns

### Pitch descriptions on one line vs separate lines

The target text often puts multiple pitches on one line:
> "Fastball. Misses just a bit outside. It's one and oh. And the 1-0... Another fastball off the plate, two and oh."

The renderer currently puts each pitch on a separate line. This is a **structural
difference in the renderer** — aligning this requires renderer changes, not just
seed/template changes. Note it and move on; these can be addressed in a later pass.

### TTS SPLIT markers

These are emitted by the renderer's pause rules for batters and pitches.
They are not packed RNG values. Changing timestamps does not select wording;
review pause/layout behavior separately from commentary draws.

### Count format: "one-oh" vs "1-0"

The renderer uses spoken words (`one-oh`) while the target sometimes uses digits
(`1-0`). This is controlled by `get_spoken_count()` in `renderers/narrative/helpers.py`.
Note any count-format mismatches — they may need a renderer change.

### Top of 6th: Summarized inning

Plays 36-38 (top 6th) have no pitch detail — they were described as a "1-2-3 inning"
in the broadcast. The renderer may need special handling for plays with empty
`pitchSequence` arrays. Check how this renders and adjust if needed.

### Top of 8th: Incomplete half-inning

Only play 50 (Winterbottom Walk) is described in the broadcast for the top 8th.
The other at-bats (Gomez, Norton) presumably happened but weren't narrated.
The renderer should handle this gracefully.

### Pitching change and pinch hitter

- Play 50: Pitching change — Chad Rosario (605112) replaces Butch Flores (645210)
- Play 58: Pinch hitter — Bartolo Johnson (545110) bats for the pitcher spot

These are detected by the renderer from matchup data changes. Verify the
pitching change announcement and pinch hitter intro render correctly.

## Full-broadcast follow-up loop

The 17 episodes now have full reviewed event ledgers, compiled Gameday fixtures,
and rendered snapshots. Follow [transcript_games/README.md](transcript_games/README.md)
for the schema and handling of partial broadcasts. A typical wording follow-up is:

```bash
python full_transcript_comparison.py 49 --gaps 5
python pbp_tools.py inspect-play examples/transcript_games/episode_049.json --play 0 -v
python pbp_tools.py search "foul back"
python fit_transcript_games.py
python full_transcript_comparison.py --check
python pbp_match_report.py --check
```

Read the cited source range before changing a ledger or pool. Append reusable
wording with its required facts, add production-path coverage, then refit and
review generated changes. `fit_transcript_games.py` rebuilds every episode and
overwrites its generated JSON/text; it searches reachable phrase choices and
stores only normal integer draw metadata. Manual changes made only to generated
JSON will be lost on refitting, so keep durable factual edits in the ledger.

The 78 representative cases remain useful for testing a specific phrase route.
Run `python transcript_comparison.py` or
`python update_transcript_examples.py --check` for those cases. Their focused
snapshots complement the full-broadcast comparisons and the original example-3
history above.
